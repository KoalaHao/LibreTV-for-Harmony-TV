# 首页滚动性能

## 已确认的代码问题与改动

v20 的首页将非懒加载 Grid / ForEach 嵌在 Scroll 中。所有已下载的推荐都会创建组件并触发图片加载，分页使节点和解码图片持续累积。标题与类型各有七层文字阴影，卡片还有圆角裁剪和火焰阴影。旧 PixelMap 缓存按 240 条计数，满时整体清空，造成再次解码。

v21 改为一个有明确视口高度的 List，加单个 LazyForEach；头部、六张一行的海报和尾部都是该数据源的行。仅创建可见部分，前后各缓存一行；分页保留完整旧行的键，末行补齐时更换其键，筛选或封面变化不会复用错误内容。滚动回调不重建数据源。

静态卡片启用 renderGroup 缓存绘制结果；悬停 / 聚焦卡片关闭该缓存以保留火焰动效，描边和文字阴影样式保留。解码缓存改为按实际 PixelMap 字节的 LRU：最多 64 MiB / 96 条，逐条淘汰；不手动释放仍被屏幕引用的 PixelMap。同图并发解码合并。销毁的图片组件不再接收迟到响应。

这与官方 [LazyForEach 指南](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/rendering-control/arkts-rendering-control-lazyforeach.md) 的有界视口及预加载要求一致。手机原有首页结构保持原流程，共用新的图片缓存。

## 代码预算，不等于实测 DRAM 流量

RGBA8、最大 600×900 解码框的单张像素上限为 2.16 MB（2.06 MiB），旧 240 条缓存的名义上限为 518.4 MB（494.4 MiB）；实际按原图比例缩放，可能小于上限。新缓存 64 MiB 是所保留 PixelMap 的字节上限，不是进程或 GPU 总内存上限。

以 555×900 像素的卡片近似，离屏绘制缓存的内容足迹约 2.00 MB / 张，12 张可见卡片约 24.0 MB 驻留；预加载行另占空间。这属于驻留预算，不能直接当作每帧搬运。缓存首次生成额外写入约 2 MB / 张；内容不变时复用，避免每次重新栅格化多层阴影。

若每帧完整读取并混合 12 张该尺寸卡片，按各读写一次的内容足迹估算约 48.0 MB / 帧、60 fps 时 2.88 GB/s 的逻辑访问；缓存、压缩和实际可见覆盖会改变外存事务。旧版基础海报合成也有这部分工作，阴影 tap 数、透明重叠、系统缓存和光栅化成本未采集，不能将 48 MB 全算成节省量。4K 最终输出尺寸没有改变。尚无有效带宽或 GPU 计数器数据，因此不推算准确帧时。

## Mate TV 原生复测

2026-10-25，OpenHarmony 6.1.1.130 / API 24。同一电影分类与列表，两版本分别重启，等待 4 秒，然后执行四次相同坐标 / 速度的下滑和四次上滑。UI 树确认全程留在首页，截图确认回到原来的一组海报，未见 ReferenceError / TypeError / SyntaxError / uncaught / ArkCompiler 错误。

单轮结束的 `/proc/<pid>/status` RSS：v20 为 303884 KiB，v21 为 194672 KiB，即约 297 MiB → 190 MiB，下降 35.9%。这是一次有限样本，不能证明所有数据量都同比下降。RenderService 没有返回可用 FPS 记录，未宣称达到稳定 60 fps，也未以屏幕刷新率当作应用帧率。
